## 1. Proofs on old WebViews

The published `@solana/zk-sdk` WebAssembly needs Chrome 96+ because it uses `externref`. Phones
without Google services ship an older WebView that can't be updated; a Huawei nova 7i has
Chrome 92. Envelope bundles the same zk-sdk version, rebuilt without WebAssembly reference types
([`build-zk-sdk-compat.sh`](../packages/cbridge/scripts/build-zk-sdk-compat.sh) reproduces it from
Solana's source).

[`compare-zk-sdk.ts`](../packages/cbridge/scripts/compare-zk-sdk.ts) checks that the rebuild is
the same cryptography:

```
1. WebAssembly features
  ok   published @solana/zk-sdk uses externref (Chrome 96+)
  ok   vendored build has no externref (Chrome 85+)
2. keys from the same seed
  ok   ElGamal public key (d22d4b5b2d768500…)
  ok   ElGamal secret key
  ok   AE key (decryptable balance)
3. ciphertexts and commitments with a fixed opening
  ok   ElGamal ciphertext
  ok   Pedersen commitment
  ok   published ciphertext decrypts in the vendored build
  ok   vendored AE ciphertext decrypts in the published build
4. proofs made by one build verify in the other
  ok   PubkeyValidityProofData: published → vendored
  ok   PubkeyValidityProofData: vendored → published
  ok   PubkeyValidityProofData: a tampered proof is rejected
  …  (same three checks for ZeroCiphertext, CiphertextCommitmentEquality, BatchedRangeProofU64)
zk-sdk builds match
```

Keys, ciphertexts and commitments are byte-identical. Proofs use fresh randomness each time, so
for them the check is that a proof made by either build verifies in the other, and a tampered one
doesn't.

On a real device: our demo video was recorded on a Huawei phone whose WebView is Chrome 92.
Every proof in it was generated by this build.

Each batch transfer carries three ZK ElGamal proof accounts. The second transfer's proofs are
built on the balance the first one leaves, which the phone works out from the ciphertext before
the wallet opens. That is how a batch needs only one approval.

**The privacy negative checks** scan the raw bytes of every transaction in the contribution and
the batch. They look for the transferred amount encoded as the `u64` a normal token transfer
would carry, and check that the recipients' token-balance metadata never moves off 0. The amounts
weren't found anywhere. A second check shows that a pot's decryption key can't be derived by
anyone but the host: it comes from the host's wallet signature, so another wallet asking for "the
same pot" gets an unrelated key.

## 4. The automated scanners' "high" Anchor leads

Automated scans flag `init_if_needed` on `user_daily` (`wrap.rs`) and `stake_position`
(`stake.rs`), and possible type cosplay in `wrap`'s stake-position read. Why none of them is
exploitable is in [THREAT_MODEL.md](../THREAT_MODEL.md#automated-security-scans--triage). These
Anchor tests pin each one down, asserting the exact error (Anchor's `ConstraintSeeds`, 2006):

- `init_if_needed on user_daily: a second wrap updates the same record, never re-creates it`
  (with a different rent payer on the second wrap, as the app's gas tank does)
- `rejects another wallet's daily record: it's bound to the signer by its seeds`
- `type cosplay: rejects another wallet's real StakePosition in the stake_position slot`
- `type cosplay: rejects a different envelope_stake account type (a Pass) as the stake position`
- `init_if_needed on stake_position: rejects staking into another wallet's position`

The full suite passes: 36/36.

## 5. Phone behaviour: background network and biometrics

[`network-retry.test.ts`](../src/utils/network-retry.test.ts) covers Android 16 blocking the app's
network while it's in the background (for example while the user is in their wallet). The first
requests after returning fail DNS:

- connection failures are retried until the network is back;
- anything else (for example insufficient funds) is rethrown at once;
- it gives up after a bounded window rather than looping forever.

[`secure-store.test.ts`](../src/features/keys/secure-store.test.ts) covers the biometric unlock:

- the key-derivation signature is stored only behind the biometric gate;
- on phones that can't gate storage (Huawei phones without Google services report "Biometric
  authentication status is unknown"), nothing is saved and the app carries on: it's never stored
  without the gate, and the next open asks the wallet to sign again;
- restoring reads it back behind the biometric prompt, and a cancelled prompt counts as "not
  unlocked yet", not an error.

In the demo video, each private send is confirmed with the fingerprint before it's proved and
sent.
